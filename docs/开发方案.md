# Windows 本地加密备忘录开发方案

## 1. 产品范围与设计约定

面向个人 Windows 电脑，首版目标环境为 Windows 11 x64。安装、建库、解锁、搜索、编辑和恢复均可断网完成。安装包自带运行时和依赖。应用无账号系统、网络服务、遥测或在线更新。一个 Windows 用户默认使用一个库。

记录分为账号与笔记。账号包含标题、网址、用户名、密码、标签和备注；笔记包含标题、标签和正文。两类记录共用随机条目 ID 和创建、修改时间。应用支持新增、搜索、编辑、删除、撤销未保存的修改、复制、手动锁定、改口令和加密备份。附件与多端同步留待另行设计。

**“存入 App 内”的具体约定**为当前 Windows 用户的应用专用注册表。业务数据存入本地 JSON。口令仅用于解开随机私钥，程序保存加密后的私钥。注册表可被当前用户的其他程序读取，因此私钥保护依靠口令加密。拿到备份的人可以离线猜测口令。已解锁进程中的明文、键盘记录、恶意程序篡改 EXE 以及旧库整体回滚均超出本方案的保密或完整性保证。

## 2. 技术栈与模块边界

桌面界面采用 C#、.NET 10 和 Windows App SDK 的 WinUI 3，使用 XAML 描述建库、解锁、列表及编辑区。解决方案入口为 `SecureMemo.slnx`。口令验证在后台执行，编辑和防抖保存由窗口队列串行处理，记录由 System.Text.Json 序列化。

    WinUI 3 窗口 → Session（解锁状态、当前记录）
                                ├─ CryptoService → 派生、封装、认证
                                ├─ KeyStore → 当前用户注册表
                                └─ VaultStore → 密文文件、替换、备份

用 .NET 的 RandomNumberGenerator、AesGcm、HMACSHA256 和 CryptographicOperations 处理随机数、私钥保护、写入认证及缓冲区清理。HPKE 和 Argon2id 采用具备标准测试向量的库实现。阶段一可评估 Bouncy Castle C# 的对应实现；选定依赖前必须验证目标套件互通、许可证、自包含发布以及离线安装，随后锁定包版本。禁止在业务代码中自行拼接曲线运算实现 HPKE。

## 3. 存储设计与协议

| 位置 | 内容及生命周期 |
|---|---|
| 当前用户注册表 HKCU\\Software\\SecureMemo\\Vaults\\{vaultId} | 一个版本化二进制值保存整个密钥信封。包含公钥、派生参数、盐、nonce、标签及加密的秘密材料。改口令时一次替换整个值。 |
| %LOCALAPPDATA%\\SecureMemo\\vault.json | 外层容器包含 formatVersion、vaultId、enc、ciphertext、writeMac。enc 为 HPKE 新封装的公开输出，ciphertext 包含 HPKE 认证标签。 |
| 加密的内层 JSON | schemaVersion、revision、entries。标题、用户名、时间和标签均在这里。搜索索引仅存在于解锁会话。 |
| 同目录临时文件及上一版副本 | 仅保存完整密文容器。上一版用于写入故障恢复，同盘副本不能解决硬盘损坏。 |
| 用户主动导出的备份 | 汇集业务容器及其对应的完整密钥信封；携带备份时保管好当时的口令。 |

协议 v1 固定密码套件。二进制字段在 JSON 中采用标准 Base64。认证输入统一用明确编码的字节串：固定用途标记、版本、库 ID 及所需字段依次编码，每个字段前置四字节大端长度。库 ID 使用小写带连字符 UUID 的 ASCII 表示，数值字段采用四字节大端无符号整数。将两组编码样例固化为测试夹具，避免不同序列化器的缩进、排序或 GUID 字节序影响验证。

读取前限制文件大小（首版建议业务文件上限 16 MiB），检查字段类型、重复属性、版本、Base64 长度和算法白名单。v1 只接受发布时确定的一组派生参数。保存前检查最终密文容器也满足读取上限。备份单独设置足以容纳最大库和信封的上限。未知版本保留原件并提示使用兼容版本。

## 4. 核心流程与原理

### 4.1 建库与口令保护

    安全随机源 → X25519 密钥对 + 独立 32 字节写入认证密钥
    口令 + 随机盐 → Argon2id → 32 字节口令派生密钥
    私钥 + 写入认证密钥 → AES-256-GCM → 密钥信封 → 注册表

首次使用时输入并确认口令。口令按 UTF-8 原样编码，保留空格；盐 16 字节。Argon2id v1.3 初始配置为 64 MiB、3 次迭代、并行度 4，在最低配置上实测解锁耗时。内存成本提高批量猜测口令的代价。AES-GCM 使用新随机 12 字节 nonce 和 16 字节标签，将信封用途、版本、库 ID、公钥、派生参数和盐作为附加认证数据。解封后核对私钥导出的公钥。

建库先写密钥信封并回读验证，再提交空库。中断后若仅有信封，可恢复初始化；若已有业务文件却找不到匹配信封，则进入恢复流程。禁止用新生成的密钥覆盖旧库。

### 4.2 保存与写入者验证

    条目快照 → UTF-8 JSON → HPKE 用公钥加密 → enc + ciphertext
    写入认证密钥 + 外层字段 → HMAC-SHA256 → writeMac
    完整容器 → 同目录临时文件 → 刷盘 → 验证 → 替换正式文件

使用 RFC 9180 Base 模式，套件为 DHKEM(X25519, HKDF-SHA256)、HKDF-SHA256、AES-256-GCM。每次保存创建新发送上下文并只 Seal 一次。HPKE 利用临时密钥和接收方公钥派生该次加密的对称密钥与 nonce，接收方用私钥得到相同结果。info 绑定应用、用途及协议版本，AAD 绑定库 ID。具体 nonce 交给标准库管理。

公钥可以被复制，其他人也能用它创建新密文。首版要求解锁后才能修改，因此增加独立 HMAC，覆盖用途、版本、库 ID、enc 和 ciphertext。全部验证通过后才接受记录。HMAC 无法判断一份真实的旧文件是否曾被回滚。

同一库持有排他写锁；手动保存、自动保存和关库共用串行写入队列。捕获快照时记录编辑版本，提交完成只确认对应版本，期间发生的新编辑继续排队。同卷写临时文件并强制刷盘，重新读取后验证 HMAC 和解密结果，已有库调用 File.Replace 保留上一版，首次建库用同卷移动且禁止覆盖。磁盘满、磁盘权限变化或替换失败时保留旧库与未保存编辑，提供重试及另存加密备份。

### 4.3 解锁、搜索与锁定

    口令 → 解封私钥及认证密钥 → 核验文件 HMAC → HPKE Open
         → 验证内层结构 → 展示记录 → 建立内存搜索索引

密钥信封认证失败时提示“口令错误或密钥信息已损坏”；信封认证成功但数据验证失败时提示“数据文件损坏或与当前库不匹配”，提供恢复入口。只有验证完成后才加载编辑界面。搜索匹配标题、用户名和标签，避免为方便搜索建立明文磁盘索引。

状态流为“锁定 → 解锁中 → 已解锁 → 锁定中 → 锁定”。手动锁定、会话锁屏和默认闲置五分钟均触发锁定。先遮住界面、禁止新编辑并完成待保存任务，再清理快照、绑定、搜索结果和可覆写的密钥缓冲区。保存失败时保持界面遮挡，保留待保存编辑，重新验证口令后允许重试。托管字符串无法保证彻底擦除，减少复制和驻留时间。日志只记录错误类型和操作阶段。

### 4.4 改口令与迁移

    旧口令 → 验证并取出原秘密材料 → 新盐 + 新口令 + 新 nonce
           → 生成新信封 → 内存验证 → 替换注册表值 → 回读验证

改口令保留原密钥对和写入认证密钥，业务密文无需重写。旧备份仍可用旧口令打开，也能恢复原私钥；若私钥已经泄露，需要生成新密钥对和认证密钥，并重新加密当前库。首版向用户明确改口令的这一边界。

    导出 → 锁定保存队列 → 获取同一已提交版本的数据和信封 → 写备份
    恢复 → 暂存 → 用备份口令解封 → 验证并解密全部记录 → 提交

恢复建议导入为独立的新库：验证成功后生成新库 ID 和密钥材料，用用户设定的口令重新封装并重新加密数据，写入独立目录和注册表项。待回读验证成功，再切换当前库指针。任一步中断，原库仍可打开。忘记口令时无在线重置渠道。卸载默认保留库和注册表密钥，彻底删除需用户明确选择。

## 5. 界面与交互

首次启动提供“新建保险库”和“恢复备份”。主界面左侧显示搜索和条目列表，右侧编辑详情，工具栏提供新增、保存和锁定。密码默认遮挡，按住显示、松开隐藏。复制密码时尽可能禁止进入系统剪贴板历史和云剪贴板；默认 30 秒后检查序列号，仅清除本次复制内容。关闭窗口遇到保存失败时保留恢复入口。

设置页提供闲置锁定时间、修改口令、导出与恢复备份。恢复前展示备份库 ID、可读条目数和目标位置；密码及正文不进入确认弹窗。密码生成器使用系统安全随机源和无偏随机索引。所有敏感操作提供键盘路径，方便仅用键盘操作。

## 6. 实施顺序、交付与验收

按一名熟悉 C# 的开发者估算，以下为开发排期参考，第三方库验证和异常恢复测试会影响工期。

| 阶段 | 预计工作日 | 可验收成果 |
|---|---:|---|
| 密码协议原型 | 2–3 | 固化格式和编码样例；通过 RFC 测试向量、中文口令往返和篡改测试，记录最低配置派生耗时。 |
| 存储与会话 | 3–4 | 建库、解锁、串行保存、原子替换、改口令；通过故障注入与双开测试。 |
| WinUI 3 交互 | 3–4 | 两类记录、搜索、编辑、复制、锁屏、错误处理和键盘操作全部可用。 |
| 恢复与发布 | 3–4 | 异机恢复成功；离线安装包、卸载保留策略、版本迁移说明及测试记录齐备。 |

**发布前测试清单**

- 加密正确性：修改公钥、信封标签、库 ID、enc、密文或 HMAC 均不得加载记录；用公开公钥构造的新密文也应验证失败。
- 数据耐久性：在写临时文件、刷盘、替换、切换恢复库的各个阶段强制结束进程，重启后能打开上一个或新提交的完整版本。
- 用户操作：保存期间继续编辑、连续按保存、双开、立即锁屏、剪贴板被其他应用更新，核对最新编辑和剪贴板内容。
- 格式边界：空库、中文和表情、多行正文、超大文件、错误参数、重复字段、未知版本均有明确结果，失败不改原件。
- 恢复能力：全新 Windows 用户仅凭备份和对应口令完成恢复；仅持业务 JSON 时明确提示缺少密钥。改口令后分别验证新旧备份的口令要求。
- 隐私与交付：断网全流程运行；用虚构账号检查日志、临时文件和备份中无明文；在无开发环境的干净机器安装、升级、卸载并重装。

**实施优先级建议**：先做一个能在第二台机器恢复的最小保险库，再接入真实账号和完整 UI。开工前确认最低配置、最大文本库容量和安装包签名方式；发行前安排独立人员复核协议编码、密钥生命周期与故障恢复。

## 7. 实现依据

- Argon2id 参数选择与测试向量见 [RFC 9106](https://www.rfc-editor.org/rfc/rfc9106.html)。
- HPKE 套件、单次加密和测试向量见 [RFC 9180](https://www.rfc-editor.org/rfc/rfc9180.html)。
- .NET 私钥信封实现参考 [Microsoft AesGcm](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.aesgcm)。
